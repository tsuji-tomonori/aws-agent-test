テストケースを作る前に、何を固定し、何を合格と呼ぶかを決めます。評価対象はモデル名ではなく、実際に回答を生む構成全体です。

<CardGrid>
  <Card title="Agent" icon="seti:config">model / CLI / reasoning設定</Card>
  <Card title="指示" icon="document">prompt / output schema / rules</Card>
  <Card title="道具と権限" icon="puzzle">MCP / public data / sandbox / IAM</Card>
  <Card title="試験問題" icon="approve-check-circle">case / input / oracle / rubric</Card>
</CardGrid>

<Steps>

1. ### 評価の問いを一文にする

   <ConsoleStep title="今回の問い" label="WORKSHEET">

   **固定したAgent構成は、CloudFormationからAWS月額を見積もるとき、情報不足なら推測せず質問し、情報が十分なら必要サービス・式・根拠をJSONで返せるか。**

   </ConsoleStep>

   「AWSに詳しいか」のような広すぎる問いは、失敗理由を特定できません。観察できる振る舞いへ落とします。

2. ### 実験条件を凍結する

   `workshop/manual/experiment.json`を作ります。値は自分の環境へ合わせてください。

   ```json
   {
     "experiment_id": "cost-estimation-prompt-v1",
     "agent_cli": "codex",
     "agent_cli_version": "記録する",
     "model": "記録する",
     "prompt_version": "agent-v1",
     "tool_mode": "no-mcp",
     "permission_mode": "read-only",
     "case_set": ["cfn-missing-usage", "cfn-static-site"],
     "repetitions": 5
   }
   ```

   prompt、model、MCP、権限のどれかを変更したら、新しい`experiment_id`にします。

3. ### 決定的ゲートを決める

   <ConsoleStep title="コードで判定する条件" label="GATE">

   | 条件 | 不合格にする例 |
   |---|---|
   | JSON契約 | 必須field欠落、型違反、JSON以外の出力 |
   | 安全 | AWSリソース作成、入力ファイル変更 |
   | 対象網羅 | 必須サービスの欠落 |
   | 算術 | 内訳の和と合計が不一致 |
   | 根拠 | 必須の一次情報URLがない |
   | 情報不足 | 値を捏造し、確認質問を返さない |

   </ConsoleStep>

   これらは正誤をコードで決められるため、LLM Judgeへ渡しません。

4. ### LLM Judgeへ残す条件を決める

   仮定の明確さ、不確実性の扱い、除外事項の明確さ、第三者が再計算できる説明か、の4点だけをJudgeへ任せます。

   <Aside type="caution" title="平均点で相殺しない">
     必須サービスを落とした回答が文章品質5点でも、総合結果は不合格です。`deterministic_pass AND semantic_pass`を総合合格とします。
   </Aside>

5. ### 1 trialの独立性を定義する

   1 trialは「新しい会話、新しいworkspace、同じ入力で1回実行」です。前回の会話をresumeせず、別trialの出力も見せません。これを守らない反復は、独立試行として集計できません。

</Steps>

<ExpectedResult title="この章の成果物">

`experiment.json`と、決定的ゲート／Judge rubricの責務分担が完成しています。まだAgentは実行しません。

</ExpectedResult>
